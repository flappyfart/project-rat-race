# verification standards

## execution is not correctness

A zero exit code and printed output are not an assertion suite. The work verifier executes explicit positive and invalid-input cases inside the isolated runner. Its deliberately incorrect negative control must fail. Publication checks bind verification to the current source hash.

These checks prove the declared cases were exercised. They do not prove all requirements, all possible inputs or commercial demand.

## independent checks

Use an operator-controlled acceptance test in addition to generated tests. Exercise the actual interface, including invalid inputs, rather than checking only a title or rendered heading.

## covered boundaries

- no official activity from page visits or client activation flags
- chain, launch receipt, contract and timestamp validation
- market identity, raw-payload binding and stale-data handling
- reachable, reproducible topology and legal exit routes
- persisted state, corruption refusal and restart continuity
- read-only endpoints, path traversal and symlink boundaries
- bounded wallet routes, ambiguous submission recovery and duplicate-payment protection
- fresh credit admission, protected reserves and automatic resumable waiting
- screenshot identity, stale/offline labels and no fabricated observations

Offline fixtures are labeled as fixtures. They are not proof that a real token was launched or that a live payment occurred. Operator financial evidence is not included in this public repository.

## biological and economic claims

The project does not claim a full biological brain emulation, consciousness, market prediction, guaranteed return or proven self-sustaining income. Those are not conclusions of software tests.
